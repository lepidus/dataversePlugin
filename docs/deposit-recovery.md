# Interrupted deposits (OJS 3.3)

Upgrade the plugin database before enabling this version. `dataverse_deposits` records a unique operation per submission, its DOI, source file manifest and confirmed remote file receipts. Only a completed operation creates the ordinary study association. Existing study rows are preserved, including legacy duplicates.

The OJS 3.3 schema does not add a foreign key to `submissions`, matching the plugin's existing study table. If a submission is deleted, its operation record remains for administrative review; submission IDs are generated by the core and are not reused in normal operation.

The manifest fixes source IDs, names, sizes and SHA-256 hashes. Upload receipts may contain multiple remote IDs for an extracted archive. The plugin never infers successful ingestion from matching names or file counts. A retry in `ready` resumes the saved DOI and skips confirmed uploads. A stale request cannot overwrite a newer revision.

`creating` or `uploading` means a mutation started without a durable confirmation (including a process crash). Requests in these states are blocked. Elapsed time does not prove the mutation failed. There is no automatic deletion or second creation, even when the remote call returns an error: some error paths may occur after the server committed the operation.

## Administrative reconciliation

This release deliberately requires repository and journal administrators to reconcile unknown outcomes. It provides no public endpoint to override the record. Do not change production records without authorization for the specific submission.

1. Pause requests for the affected submission and ensure the original PHP request has ended. Back up its `dataverse_deposits`, `dataverse_studies` and draft-file records. Inspect only the targeted submission, its configured repository and the source manifest.
2. For `creating`, obtain authoritative repository evidence linking the original request to the created DOI (server request/audit record, authenticated depositor and exact deposit metadata). Titles, times or file counts alone are insufficient. If the repository proves that no creation occurred, the operation may be returned to `reserved`. Otherwise preserve the block until the DOI is identified.
3. For `uploading`, use repository request/audit evidence to identify the files created by that particular upload. Validate the complete set, including archive extraction and tabular conversion. Store the exact remote IDs, checksums and sizes as that source's receipt. If the repository proves no upload occurred, leave that source without a receipt. If evidence is incomplete, retain `uploading` and do not repeat the upload.
4. Apply the verified DOI and receipts in a short database transaction scoped by `submission_id`, the inspected `state` and `revision`. Increment `revision` and move to `ready` only after every uncertain mutation has been resolved. Require exactly one affected row. Do not insert a study for an incomplete operation or delete temporary source files.
5. Restore the exact original source selection if it changed. Retry through the authorized OJS submission flow and verify the association and all uploaded research files before publication.

An explicit successful deletion or disassociation retires the completed operation under the submission lock. Its revision remains monotonic. A later deposit may reset that retired record to a new source manifest; manual association is also allowed. Unknown operations cannot be retired this way. Rows are never deleted or reset to revision zero, which would allow a stale worker to claim a new operation.

This mechanism cannot guarantee remote exactly-once execution without server-side idempotency. It prevents automated repetition of uncertain mutations, and preserves enough evidence for explicit recovery. Existing orphan datasets are not automatically removed or associated.
